## 一、功能背景

「特征库」是系统里唯一需要被用户**直接管理**的数据：录错了要删、录了谁要能查、库里有多少人要可见。CLI 已有两项能力：

| CLI 功能 | 实现 | Web 化障碍 |
|----------|------|------------|
| `show_all_features()` | `get_all_features()` → 打印矩阵形状 + `[{id, name}]` | 只返回 `id/name`，**没有录入时间**；且顺带把 2048 B/条的 BLOB 全量反序列化，对「列表展示」是浪费 |
| `delete_face()` | `input()` 取姓名 → `db_utils.delete_by_name()` | 依赖控制台输入，且不返回结构化结果 |

因此接口层需要提供**两个只读/管理型接口**：

1. `GET /api/face/library`：返回特征库全部记录的元信息（ID、姓名、录入时间、特征维度），供 `FaceLibrary.vue` 表格渲染；
2. `DELETE /api/face/library?name=xxx`：按姓名删除，返回实际删除条数，供列表页「删除」按钮调用。

**关键设计决策**：列表接口**不复用** `get_all_features()`。原因：

| 维度 | `get_all_features()` | 列表接口需要 |
|------|----------------------|--------------|
| 返回内容 | `(N,512)` 特征矩阵 + `[{id, name}]` | `id / name / timestamp / feature_dim` |
| BLOB 读取 | 全量读取并反序列化（2048 B × N） | 不需要特征本体 |
| 录入时间 | 查询里没有 `timestamp` 列 | 必须有 |
| 用途 | 识别比对 | 库管理展示 |

故 Step 3-4 在 `db_utils.py` 中**新增** `list_records()`（纯 SELECT，不改变既有方法语义），供接口层调用。

## 二、开发目标

| 目标 | 说明 |
|------|------|
| 列表可读 | 返回 `total` + `items[]`，每项含 `id / name / timestamp / feature_dim` |
| 排序稳定 | 按 `id` 升序（录入先后），避免同一请求多次刷新顺序跳动 |
| 空库友好 | 空库返回 `code=0, total=0, items=[]`，不报错、不 404 |
| 按姓名删除 | query 参数 `name`，返回实际删除行数；0 行返回 `1005` |
| 中文可用 | 姓名含中文可正常查询/删除（UTF-8 URL 编码） |
| 类型安全 | `name` 为必填 query 参数（完全缺失 → `422`）；空串/纯空白在路由内 `strip()` 后拦截 → `1001` |
| 轻量查询 | 列表 SQL 不读取 `feature` BLOB，1000 条仅返回几十 KB JSON |
| 结果可观测 | 删除操作记录 `logging.info`（姓名、行数、耗时） |

## 三、功能职责

| 分类 | 函数 | 职责 |
|------|------|------|
| 数据层（新增） | `FaceFeatureDB.list_records() -> list[dict]` | 只读元信息，按 `id ASC`，字段 `id/name/timestamp/feature_dim` |
| 路由 | `get_library()` | 组装 `LibraryData{total, items}` |
| 路由 | `delete_library_item(name)` | 姓名规范化 → 删除 → 组装 `DeleteData{name, deleted}` |
| 校验 | `_normalize_name(name)` | `strip()` → 非空校验（与 3-2 入库口径一致） |

**不做的事**：

- 不做「按 ID 删除」（业务模型是「同名即同一人」，见 `docs/02-03` 坑点 5）；
- 不做重命名 / 覆盖更新（覆盖 = 删除后重新录入）；
- 不做批量删除、导出 CSV（后置增强项）；
- 不返回特征向量本体（体积大且无展示意义）；
- 不做分页（千级规模无需；如需要见坑点 10）。

## 四、功能逻辑

### 4.1 接口定义

| 接口 | 方法 | 路径 | 参数 | 成功响应 `data` |
|------|------|------|------|-----------------|
| 特征库列表 | `GET` | `/api/face/library` | 无 | `LibraryData{total, items[]}` |
| 删除特征 | `DELETE` | `/api/face/library` | `name`（query，必填） | `DeleteData{name, deleted}` |

```python
@app.get('/api/face/library', response_model=ApiResponse[LibraryData], tags=['library'])
def get_library():
    records = db_utils.face_db.list_records()
    return ok(LibraryData(total=len(records), items=records),
              message=f'共 {len(records)} 条特征记录')


@app.delete('/api/face/library', response_model=ApiResponse[DeleteData], tags=['library'])
def delete_library_item(name: str = Query(..., description='要删除的姓名')):
    name = name.strip()
    if not name:
        return fail(1001, '姓名不能为空或纯空格')
    try:
        deleted = db_utils.face_db.delete_by_name(name)
    except Exception:
        logging.exception('删除特征失败: name=%s', name)
        return fail(1007, '删除失败，请查看服务端日志')
    if deleted == 0:
        return fail(1005, f'特征库中不存在姓名: {name}')
    logging.info('删除特征成功: name=%s deleted=%d', name, deleted)
    return ok(DeleteData(name=name, deleted=deleted),
              message=f'已删除 {deleted} 条「{name}」特征')
```

> **注意**：`delete_by_name()` 内部自带 `commit()` 和 `print()`。接口层只负责「参数校验 + 错误码映射 + 结构化返回」，不重复打印；该 `print` 会输出到 uvicorn 控制台，可在阶段 5 统一替换为 `logging`。

```json
  }

```

**空库**

```json
{"code": 0, "message": "共 0 条特征记录", "data": {"total": 0, "items": []}}
```

**删除（中文需 URL 编码）**

```powershell
curl.exe -X DELETE "http://127.0.0.1:8000/api/face/library?name=%E4%B8%81%E7%9C%9F"
```

```json
{"code": 0, "message": "已删除 2 条「丁真」特征", "data": {"name": "丁真", "deleted": 2}}
```

**删除不存在的姓名**

```json
{"code": 1005, "message": "特征库中不存在姓名: 不存在的人", "data": null}
```

**参数缺失 / 空白**

```json
{"code": 1001, "message": "姓名不能为空或纯空格", "data": null}
```

> `?name=`（空字符串）与 `?name=%20%20`（纯空格）都能通过 Query 必填校验，由路由内 `strip()` 统一拦截 → `1001`；完全不带 `name` 参数才由框架返回 `422`。前端两者都按「参数错误」处理。

### 4.3 列表处理流程

```text
GET /api/face/library
        │
        ├─ 1. db_utils.face_db.list_records()
        │       SELECT id, face_id, timestamp, feature_dim
        │       FROM face_features ORDER BY id ASC
        │       （不读取 feature BLOB）
        ├─ 2. 行 → dict: {id, name: face_id or '', timestamp, feature_dim}
        ├─ 3. total = len(records)
        └─ 4. ok(LibraryData(total, items))
```

| 设计点 | 取值 | 理由 |
|--------|------|------|
| 排序 | `ORDER BY id ASC` | `AUTOINCREMENT` 单调递增 = 录入先后；按 `timestamp` 排序在同秒录入时不稳定 |
| 字段 | `id / name / timestamp / feature_dim` | 前端表格展示够用；`feature_dim` 可用于排查「老库维度不一致」 |
| 空值 | `face_id` 为 `NULL` → `''` | 历史脏数据不让前端渲染出 `null` 字样 |
| 不分页 | 全量返回 | 千级记录 JSON 约 100 KB，远小于前端一次识别的图片体积 |

### 4.4 删除处理流程

```text
DELETE /api/face/library?name=丁真
        │
        ├─ 1. Query 必填校验（缺参）                          → 422
        ├─ 2. name.strip() 后为空（空串/纯空格）              → 1001
        ├─ 3. db_utils.face_db.delete_by_name(name)
        │       DELETE FROM face_features WHERE face_id = ?
        │       conn.commit()                              （事务内完成）
        ├─ 4. deleted == 0 ?                               是 → 1005
        └─ 5. ok(DeleteData(name, deleted))                同时 logging.info
```

| 场景 | 结果 | 前端表现 |
|------|------|----------|
| 姓名存在、1 条 | `code=0, deleted=1` | 提示「已删除 1 条」，刷新列表 |
| 姓名存在、多条（多次录入） | `code=0, deleted=N` | 提示「已删除 N 条」，一次清空该人 |
| 姓名不存在 | `code=1005` | 提示「该记录已不存在」，仍刷新列表 |
| 重复点击删除 | 第二次 `1005` | 幂等视角无副作用，无需特殊处理 |
| 数据库被占用 / IO 错误 | `code=1007` | 提示「删除失败」，引导看服务端日志 |

> **为什么 0 行返回 `1005` 而不是 `code=0`**：删除按钮来自列表快照，0 行意味着「你以为存在的记录已经没了」（他人删除 / 页面过期）。返回 `1005` 让前端能明确提示并强制刷新列表；前端不应把它当致命错误弹窗，用 `ElMessage.warning` 即可。

### 4.5 数据层新增方法

```python
# db_utils.py · FaceFeatureDB 新增（只读，不改变既有方法语义）
def list_records(self):
    """
    获取特征库元信息（不读取特征 BLOB），按录入顺序返回
    :return: [{'id': int, 'name': str, 'timestamp': str, 'feature_dim': int}, ...]
    """
    cursor = self.conn.cursor()
    try:
        cursor.execute('''
        SELECT id, face_id, timestamp, feature_dim
        FROM face_features
        ORDER BY id ASC
        ''')
        return [{'id': rid,
                 'name': name or '',
                 'timestamp': ts,
                 'feature_dim': dim}
                for rid, name, ts, dim in cursor.fetchall()]
    finally:
        cursor.close()
```

| 约束 | 说明 |
|------|------|
| 不改 `get_all_features()` | 识别链路依赖其返回 `(matrix, info_list)`，加字段会牵连 3-3 与测试 |
| 不返回 `feature` | JSON 里出现 2048 个浮点数既无意义又易误传 |
| 使用参数化/无参数 SQL | `list_records` 无入参；`delete_by_name` 已是 `?` 占位符 |
| 连接复用 | 沿用进程内单例 `face_db`，不新建连接（见 `docs/03-01` 4.9） |

### 4.6 与 CLI 行为对照

| 能力 | CLI | API | 差异说明 |
|------|-----|-----|----------|
| 查看库 | `show_all_features()` 打印形状 + `[{id,name}]` | `GET` 返回含 `timestamp/feature_dim` 的 JSON | API 信息更全，不含特征矩阵 |
| 删除 | `delete_face()` → `input()` + `delete_by_name()` | `DELETE ?name=` → 同一 `delete_by_name()` | 删除逻辑 100% 复用，计数语义一致 |
| 同名多条 | 一次全删 | 一次全删，返回 `deleted=N` | 一致 |
| 不存在 | 打印「库中没有记录」 | `1005` + 中文提示 | 一致（表达方式不同） |
| 空库 | `get_all_features()` 返回 `(None, None)` | `total=0, items=[]` | API 不把「空」当异常 |

### 4.7 并发与数据一致性

| 场景 | 行为 | 说明 |
|------|------|------|
| 识别请求进行中执行删除 | 当前请求仍用旧快照 | 识别每次请求都重新 `get_all_features()`，下一次请求即生效，无需重启 |
| 删除与录入并发 | 由 `RLock` + SQLite 事务串行化 | `save_feature` 先 `SELECT` 判重再 `INSERT`，与 `DELETE` 之间仍存在极小竞态（极端情况下删完又被录入），单用户场景可接受 |
| 前端删除后列表 | 重新 `GET` 拉取 | 不用本地 `filter` 猜测结果，避免 `deleted=N` 与本地删 1 行不一致 |
| 浏览器缓存 | `axios` 默认不加缓存头 | 如需绝对新鲜可加 `Cache-Control: no-store`（阶段 4 处理） |

## 七、异常点与坑点

| # | 问题 | 现象 | 定位与处置 |
|---|------|------|------------|
| 1 | **用 `get_all_features()` 拼列表** | 缺 `timestamp`，且每条都反序列化 2048 B 特征 | 新增 `list_records()` 只查元信息；识别链路继续用 `get_all_features()` |
| 2 | **中文 query 未编码** | `curl` 直接拼中文可能被 PowerShell 转码成乱码，DELETE 0 行返回 `1005` | 用 `%E4%B8%81%E7%9C%9F` 或 `--data-urlencode`；前端 `axios` 的 `params` 会自动编码 |
| 3 | **DELETE 用请求体传姓名** | 部分浏览器/代理会丢弃 DELETE body，`name` 变成必填缺失 → 422 | 一律用 query 参数；只读用 GET，状态变更用 DELETE，语义清晰 |
| 4 | **只靠框架校验挡空值** | `?name=` 与 `?name=%20%20` 都能进入业务，直接 `DELETE WHERE face_id=''` 命中 0 行 | 路由内 `strip()` 后校验 → `1001`；不要给 `Query` 加 `min_length`，否则空串变 `422`、纯空格变 `1001`，前端要写两套分支 |
| 5 | **0 行当成功返回** | 前端误以为删除成功，列表仍显示（或本地已移除）造成不一致 | 0 行 → `1005`，前端 `warning` + 强制刷新 |
| 6 | **只删一条同名人脸** | 若 SQL 带 `LIMIT 1`，多次录入的同名记录残留，仍能被识别命中 | `DELETE ... WHERE face_id = ?` 不带 LIMIT，一次清空；前端提示 `deleted` 条数 |
| 7 | **SQL 字符串拼接** | 姓名含 `'` 或 `%; DROP` 时报错/注入 | 坚持 `?` 参数化；`list_records` 无入参 |
| 8 | **`face_id` 为 NULL** | 历史数据/异常写入导致 `name: null`，前端 `v-for` 渲染异常 | SQL 层不用改，Python 侧 `name or ''` |
| 9 | **按 `timestamp` 排序不稳定** | 同一秒录入的多条顺序随机，刷新后行位置跳动 | `ORDER BY id ASC`（自增主键） |
| 10 | **未来加分页后 `total` 语义错** | 用 `len(items)` 当总数，分页后总数变成页大小 | 加分页时 `total` 必须来自 `SELECT COUNT(*)`；当前不分页 |
| 11 | **删除后列表未刷新** | 前端仅按 `deleted` 本地删 1 行，与「同名多条」不符 | 删除成功后无条件重新 `GET` |
| 12 | **识别侧缓存了旧矩阵** | 若为提速在进程内缓存 `library_matrix`，删除后仍能识别出已删姓名 | 本设计不缓存；如后续加缓存，删除接口必须触发失效 |
| 13 | **数据库被外部工具占用** | 用 DB Browser 打开 `face_features.db` 未关闭 → 删除报 `database is locked` | 提示关闭外部连接；服务端连接参数与写锁见 `docs/03-01` 4.9 |
| 14 | **用 GET 做删除** | 浏览器预取/爬虫误删数据 | 严格 `DELETE` 方法；CORS 允许 `DELETE`（`docs/03-01` 4.4） |
| 15 | **时间戳无时区** | `timestamp` 是本地时间字符串，跨时区部署会误解 | 本项目单机部署，原样展示；如需多时区再改为 UTC + 前端本地化 |
