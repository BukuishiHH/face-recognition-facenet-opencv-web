## 一、功能背景

「把人脸存进特征库」是全部业务的起点。阶段 2 的 CLI 已实现两条采集路径，但它们与交互强耦合：

| CLI 现状 | 耦合点 | Web 化障碍 |
|----------|--------|------------|
| `register_face_from_image()` | `input()` 取图片路径与姓名 | 浏览器没有「服务器本地路径」的概念，只能上传字节流 |
| `register_face_from_camera()` | `cv2.VideoCapture(0)` + `imshow()` + `input()` 取姓名 | 服务端没有摄像头（或摄像头在用户侧），必须由前端采集帧后上传 |

因此接口层需要提供**两种图片来源**，并共用同一段「检测 → ROI → 特征 → 入库」逻辑。

**为什么拆成两个接口，而不是统一成一个？**

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **两个接口**：`multipart` 图片 + JSON 帧 | 上传走标准表单流，浏览器可断点/限流；帧走 JSON，前端 `canvas.toDataURL()` 直接塞入，省掉一次 Blob 转换 | 两个路由，代码略有重复 | ✅ 选用 |
| 统一为 base64 JSON | 只写一个路由 | 本地大图需前端先转 base64，体积膨胀约 33%，5 MB 图变 6.7 MB 字符串 | ✗ |
| 统一为 multipart | 只写一个路由 | 前端需把 canvas 帧转 Blob + `FormData`，实时采集链路多一步异步转换 | ✗ |

**复用边界**：复用「编排逻辑」（顺序、校验、异常语义），**不复用函数本体**——`main.py` 的函数内部含 `input()`/`imshow()`，直接调用会阻塞线程池且无法测试。

## 二、开发目标

| 目标 | 说明 |
|------|------|
| 图片入库 | 上传本地图片 + 姓名 → 检测 → 取 ROI → 提特征 → 写库 → 返回记录 ID |
| 帧入库 | 接收前端摄像头 base64 帧 + 姓名 → 同上流程（供「拍照入库」使用） |
| 无人脸可读 | 未检出人脸返回 `1002`，不写库、不抛异常栈 |
| 同名防重 | 同名已存在返回 `1004`，不产生第二条记录（与 CLI 语义一致） |
| 多脸可控 | 一张图检出多张人脸时按明确策略只入库 1 张，并在响应中回传人脸总数 |
| 输入健壮 | 空姓名、超长姓名、空文件、超大文件、损坏图片、非法 base64 全部返回 `1001` |
| 可观测 | 关键节点写 `logging`（解码尺寸、检测数量、特征耗时、入库 ID），不污染响应 |

## 三、功能职责

| 分类 | 函数 | 职责 |
|------|------|------|
| 共用服务 | `_register_from_bgr(image, name) -> (code, message, data)` | 检测 → 选脸 → ROI → 特征 → 查重 → 入库，**不含任何协议解析** |
| 路由 | `register_by_image(file, name)` | 解析 `multipart`、大小校验、调用共用服务 |
| 路由 | `register_by_frame(payload)` | 解析 JSON + base64、调用共用服务 |
| 校验 | `_validate_name(name)` / `_validate_upload(file)` | 姓名去空格与长度；文件非空与 ≤ 5 MB |

**不做的事**：

- 不返回标注图（采集只需回执，结果图由识别接口负责）；
- 不做前端预览、裁剪、拍照（→ 阶段 4 `FaceCollect.vue`）；
- 不做同名覆盖（覆盖 = 先删后录，见 `docs/03-04`）；
- 不修改 `db_utils` 的查重语义，仅**新增**只读查询能力。

## 四、功能逻辑

### 4.1 接口定义

| 接口 | 方法 | 路径 | Content-Type | 参数 | 成功响应 `data` |
|------|------|------|--------------|------|-----------------|
| 图片入库 | `POST` | `/api/face/register/image` | `multipart/form-data` | `file`（必填，二进制）、`name`（必填，`Form` 字符串） | `RegisterData` |
| 帧入库 | `POST` | `/api/face/register/camera-frame` | `application/json` | `name`、`image_base64`（必填） | `RegisterData` |

字段约束：

| 字段 | 类型 | 约束 | 违规返回 |
|------|------|------|----------|
| `name` | string | 去除首尾空白后长度 1~32；不允许仅空白 | `1001` |
| `file` | binary | 非空且 ≤ 5 MB（`MAX_UPLOAD_BYTES`） | `1001` |
| `image_base64` | string | 非空、可解码、可 `imdecode`；支持带 `data:` 前缀 | `1001` |

```python
@app.post('/api/face/register/image', response_model=ApiResponse[RegisterData], tags=['face'])
def register_by_image(file: UploadFile = File(...), name: str = Form(...)):
    name = name.strip()
    if not name or len(name) > MAX_NAME_LEN:
        return fail(1001, '姓名不能为空且长度需在 1~32 之间')
    raw = file.file.read()                       # 同步路由直接读底层文件对象
    if not raw or len(raw) > MAX_UPLOAD_BYTES:
        return fail(1001, '图片为空或超过 5MB')
    image = decode_upload_image(raw)
    if image is None:
        return fail(1001, '图片损坏或格式不支持')
    code, message, data = _register_from_bgr(image, name)
    return fail(code, message) if code else ok(data, message)
```

> 路由使用**同步 `def`**：检测与特征提取是 CPU 密集操作，FastAPI 会自动放入线程池，避免阻塞事件循环；`UploadFile` 的 `await file.read()` 仅在 `async def` 中可用，同步路由应使用 `file.file.read()`。
>
> **FastAPI 0.143 实现差异**：空 `Form` 字符串会被视为字段缺失，直接 `name: str = Form(...)` 会让 `name=` 返回 422，与「空姓名返回 1001」冲突。实际实现用 `Form('')` 接收，再通过 `request._form` 是否包含 `name` 区分「字段缺失（422）」与「空/纯空格（1001）」，并在自定义 `openapi()` 中把 `name` 补回 `required`。

### 4.2 请求 / 响应示例

**图片入库**

```powershell
curl.exe -X POST http://127.0.0.1:8000/api/face/register/image `
  -F "file=@backend/sample_faces/dingzhen/dingzhen_1.jpg;type=image/jpeg" `
  -F "name=丁真"
```

**帧入库**

```json
POST /api/face/register/camera-frame
{
  "name": "丁真",
  "image_base64": "data:image/jpeg;base64,/9j/4AAQSkZJRgABAQ..."
}
```

**成功响应**

```json
{
  "code": 0,
  "message": "人脸录入成功",
  "data": {
    "record_id": 7,
    "name": "丁真",
    "face_count": 1,
    "selected": {"x": 118, "y": 64, "w": 210, "h": 210},
    "feature_dim": 512
  }
}
```

**失败响应**

```json
{"code": 1002, "message": "未检测到人脸，请更换图片或正对摄像头", "data": null}
{"code": 1004, "message": "姓名[丁真]已存在，请先删除旧记录再录入", "data": null}
{"code": 1003, "message": "人脸特征提取失败，请重试", "data": null}
```

### 4.3 处理流程

```text
POST /api/face/register/image  (multipart: file + name)
POST /api/face/register/camera-frame  (JSON: name + image_base64)
        │
        ├─ 1. 姓名校验: strip → 非空 → 长度 ≤ 32          失败 → 1001
        ├─ 2. 图片解码:
        │      上传: file.file.read() → decode_upload_image()
        │      帧  : decode_base64_image()  (剥离 dataURL 前缀)
        │      失败/空/超大                              → 1001
        │
        ├─ 3. 人脸检测: detector.detect_faces(image)     结果为空 → 1002
        │      └─ 返回 [(x, y, w, h), ...]，坐标为原图坐标系
        │
        ├─ 4. 选脸: 多脸时取面积最大的一张（见 4.4）
        ├─ 5. 截取 ROI: FaceDetection.crop_face_rois() 只取选中框
        │
        ├─ 6. 提取特征: FaceRecognition.extract_feature(roi)
        │      └─ 返回 (1,512) float32 或 None           None → 1003
        │
        ├─ 7. 同名预检: db_utils.face_db.exists_name(name)
        │      └─ 已存在                                  → 1004
        │
        ├─ 8. 入库: face_db.save_feature(feature, name)
        │      └─ 返回 None（并发/校验失败）             → 1003
        │
        └─ 9. 组装 RegisterData:
               record_id / name / face_count / selected(选中框) / feature_dim
```

> **为什么先 `exists_name` 再 `save_feature`**：`save_feature` 失败时统一返回 `None`，接口层无法区分「同名跳过」与「形状错误 / 写库异常」。预检一次即可把 `1004` 与 `1003` 分开；`save_feature` 内部的查重仍然保留，用于兜住并发窗口（见坑点 10）。

### 4.4 多脸选择策略

| 场景 | 策略 | 理由 |
|------|------|------|
| 1 张脸 | 直接入库 | 正常路径 |
| 多张脸 | 取**面积最大**的框入库，`face_count` 回传真实总数 | 合照中主体通常离镜头最近、面积最大；比「拒绝入库」体验好，也避免把背景路人当作同一人 |
| 0 张脸 | `1002` | 无可用 ROI |
| 面积并列 | 取检测顺序第一个（`detectMultiScale` 输出顺序） | 结果确定、可测试 |

多脸时前端应提示「检测到 N 张人脸，已取最大人脸入库」，由 `message` 或 `data.face_count > 1` 驱动。

### 4.5 与 CLI 实现的差异对照

| 环节 | `main.py`（CLI） | `api_server.py`（Web） | 是否复用 |
|------|------------------|------------------------|----------|
| 图片来源 | `input()` 路径 / `VideoCapture(0)` | 上传字节 / base64 帧 | ✗（协议不同） |
| 读图 | `cv2.imdecode(np.fromfile(path))` | `cv2.imdecode(np.frombuffer(bytes))` | 逻辑一致，实现不同 |
| 检测 | `face_detector.detect_faces` | `app.state.detector.detect_faces` | ✅ 同一类 |
| ROI | `crop_face_rois` | 只对选中框切片 | ✅ 同一类 |
| 特征 | `FaceRecognition.extract_feature` | 同左 | ✅ 直接调用 |
| 入库 | `face_db.save_feature` | 同左（先 `exists_name`） | ✅ 同一实例 |
| 交互 | `input()` 姓名、`imshow` 预览 | `Form` / JSON 字段、无 GUI | ✗（必须剥离） |

### 4.6 性能预算

| 环节 | CPU（经验预算，阶段 3-5 实测校准） | GPU | 说明 |
|------|--------------------------------------|-----|------|
| base64 解码 + `imdecode` | 5 ~ 20 ms | — | 与图片体积正相关 |
| Haar 检测（640×480） | 15 ~ 40 ms | — | Haar 只能 CPU |
| 特征提取（160×160） | 40 ~ 90 ms | 10 ~ 25 ms | 首次请求含预热外的首帧开销 |
| SQLite 写入 | < 5 ms | — | 单条 2048 B |
| **合计** | **60 ~ 150 ms** | **30 ~ 70 ms** | 满足「点击即回执」体验 |

## 七、异常点与坑点

| # | 问题 | 现象 | 定位与处置 |
|---|------|------|------------|
| 1 | **multipart 字段名不一致** | 前端传 `image` / `username`，后端声明 `file` / `name` → `422`，且错误信息只说 `field required` | 字段名以本文档 4.1 为契约；前端 `FormData.append('file', blob, 'x.jpg')`、`append('name', name)` |
| 2 | **同步路由里 `await file.read()`** | 同步 `def` 路由中使用 `await` → `SyntaxError`；或误写为 `file.read()` 返回字节但未做大小校验 | 同步路由统一 `file.file.read()`；`async def` 路由才用 `await file.read()` |
| 3 | **`python-multipart` 缺失** | 启动即报 `RuntimeError: Form data requires "python-multipart" to be installed` | 阶段 1 已安装，接口自检时确认 `import multipart` 成功 |
| 4 | **dataURL 前缀** | `b64decode('data:image/jpeg;base64,...')` 抛 `binascii.Error: Invalid base64-encoded string` | `decode_base64_image()` 统一剥离 `data:` 前缀并去除空白 |
| 5 | **base64 体积膨胀** | 5 MB 图 → 6.7 MB JSON；实时帧若传原尺寸会拖慢解析 | 前端摄像头帧统一 640×480、JPEG 质量 0.8（约 30~80 KB）；后端仍保留 5 MB 上限兜底 |
| 6 | **多人脸误入库** | 合照中把背景路人特征记到同一姓名下，导致后续识别误命中 | 只取面积最大的一张入库，并在 `face_count > 1` 时提示用户；确需多角度样本请多次单人采集 |
| 7 | **同名判断依赖返回值 `None`** | `save_feature` 对「同名」与「形状错误」都返回 `None`，接口无法区分 | 入库前 `exists_name()` 预检 → `1004`；`save_feature` 返回 `None` 时归为 `1003` 并记录日志 |
| 8 | **`extract_feature` 吞异常** | 模型异常在 `face_recognition.py` 内部被 `try/except` 捕获并 `print`，只返回 `None` | 接口层必须判 `None` → `1003`；同时通过 `logging` 记录上下文，避免只有一行 `print` |
| 9 | **PNG 4 通道 / 灰度图** | 直接传 ROI 给模型时通道数不符 → `cvtColor` 报错 | `cv2.imdecode(..., cv2.IMREAD_COLOR)` 强制 3 通道，统一入口即可规避 |
| 10 | **并发同名录入竞态** | 两个请求同时通过 `exists_name` 预检，随后各插入一条同名记录 | `save_feature` 内部查重 + 数据库写锁（03-01 4.9）；根治可给 `face_id` 加 `UNIQUE` 索引，但需先清理历史重复数据 |
| 11 | **中文姓名在命令行丢失** | `curl -F "name=丁真"` 在部分终端编码下变乱码，入库姓名错误 | PowerShell 中可改用文件上传 + `/docs` 测试；接口本身按 UTF-8 解析，无需额外处理 |
| 12 | **返回框坐标与前端不一致** | 前端把 `selected` 直接叠加到预览图，但预览图是缩放后的 | 采集页无需叠加；若需展示，按 `previewWidth / naturalWidth` 缩放，见 `docs/04-02` |
| 13 | **`exists_name` 全表扫描** | 数据量大时每次录入都扫全表 | 千级规模无感；可在 `face_id` 上建普通索引（与坑点 10 的 UNIQUE 索引一并考虑） |
